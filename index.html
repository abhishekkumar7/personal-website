Teaching resource 01

Build an AI-powered web app

A starter kit for classes that want students to build and test a small AI app. A team goes from an idea to a working prototype on their own computer, then improves it step by step with an AI coding assistant.

  • MBA, executive and doctoral classes
  • About an hour to a first version
  • No programming background needed
  • Works on macOS and Windows
Download the starter kit (zip) Start at step 1

What this kit is for

The kit gives a team a small working app to start from, so nobody begins with a blank screen. You decide what the app should do, ask an AI coding assistant to customise the starter, run it on your own computer, and keep improving it.

The aim is not to turn anyone into a software engineer. It is to understand the workflow behind most AI apps: a person types a request, the app sends it to a language model through an API, the model answers, and the app shows the result. A synthetic dataset is fine for a demo, and an app may build just one useful slice of a bigger idea.

Show commands for

Phase 1Set up

You will use the terminal built into your computer: Terminal on macOS, PowerShell on Windows. In the code blocks, type only the command, not the $ or PS> at the start. The Copy button leaves those out for you.

1

Get the starter files

  1. Download AI_App_Development_Kit.zip and unzip it.
  2. Move the folder to your Desktop and rename it myapp.

Files ending in .md or .env, such as AppPlan.md and local.env, are plain text. Open them in Notepad on Windows or TextEdit on macOS (in TextEdit choose Format → Make Plain Text before you save).

2

Open the folder in an AI coding assistant

Use any assistant that can read and edit files in a folder, for example Claude Code, Codex or Cursor. Your instructor will tell you which one the class uses. Open the myapp folder in it.

Then ask it to read before it writes:

Say this to your assistant
Read AppPlan.md and README.md in this folder. Do not change anything yet. Tell me what you understand about the project.
3

Install Node.js

Node.js lets the starter app run on your computer. It comes with npm, which starts the app. The starter needs version 18 or newer and has no other packages to install.

  1. Go to nodejs.org/en/download and install the version for your computer (the macOS Installer, .pkgWindows Installer, .msi).
  2. Open Terminal.
  3. Open the Start menu, search for PowerShell and open it.
  4. Check that both tools are installed. Each line should print a version number.
macOS
$ node --version
$ npm --version
Windows
PS> node --version
PS> npm --version
4

Get an API key

An API key is a long secret code that lets your app talk to a language model. The starter uses Google's Gemini models, and Google's API has offered a free tier that is usually enough for class exercises (check the current limits). Ask your instructor if the class uses a different provider; your assistant can switch the starter over.

  1. Sign in to a Google account. A personal account is simplest if a school or work account blocks key creation.
  2. Open aistudio.google.com/app/apikey and choose Create API key. If asked, create it in a new project.
  3. Copy the key when it appears. It looks like a long string of letters and numbers.
Treat the key like a password.Do not paste it into a chat with your assistant, a document, a screenshot or a shared folder. Set a spending limit in the provider's console if it offers one.
5

Put the key in local.env

Open local.env in a plain-text editor and replace your_real_key_here with your key. Save the file.

local.env
GEMINI_API_KEY=your_real_key_here
GEMINI_MODEL=gemini-2.5-flash

No key yet? Skip ahead. The starter runs in demo mode and answers with a short message, so you can see the page working before the key is ready.

Phase 2Prototype locally

Everything from here runs on your own computer. You do not need to finish the whole product. Get a basic version working, then keep building in Phase 3.

6

Write the plan in AppPlan.md

Open AppPlan.md and fill in the app idea: the use case, the intended user, what the user types, what the model should return, how the model will be guided, and whether the app needs source material or data. This is your direct instruction to the assistant. Perfect is not the goal. A clear, simple first version is.

If your app depends on a specific dataset, you can use a classic machine learning model, such as a decision tree or a gradient-boosted model, instead of a language model. Tell your instructor, because the setup changes.

7

Ask the assistant to build version one

Use the strongest model and the deepest reasoning setting your assistant offers for this first build. Use a lighter setting for small edits such as wording or colours.

Say this to your assistant
Read AppPlan.md and README.md. Before editing, summarise the app's purpose, the user, the inputs and outputs, and the behaviour the system prompt has to produce. Then build the first working version using the files already in this folder. Treat the design notes in AppPlan.md as requirements. Put the system prompt in one clearly labelled place in server.js so I can edit it. Keep it simple, make it run at http://localhost:3000, and do not add accounts, databases or logins.
8

Run it on your computer

In the terminal, move into the folder and start the app.

macOS
$ cd ~/Desktop/myapp
$ npm start
Windows
PS> cd "$env:USERPROFILE\Desktop\myapp"
PS> npm start

Open http://localhost:3000 in your browser. The command keeps running while the app is alive. When you finish testing, click the terminal and press Ctrl+C to stop it.

If you see "port 3000 is already in use", another copy is still running. Close other terminal windows and assistant previews, or clear the port:

macOS
$ lsof -ti tcp:3000 | xargs kill
Windows
PS> Get-NetTCPConnection -LocalPort 3000 | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
9

Test it with three questions

Before you change anything, try the three test questions from AppPlan.md: a typical one, a tricky one and an off-topic one. Write down what the app did. You will repeat these tests after every change in Phase 3, and the comparison is how you know whether a change helped.

Phase 3Iterate

Once the first version runs, improve it. Change one thing at a time so you can tell what each change did.

10

Pick one improvement

Choose a single next step. Good candidates:

  • A clearer app name and one-line description
  • A cleaner visual design
  • A better example question on the page
  • A more specific system prompt
  • A new input field, such as a dropdown for audience or tone
  • A more useful answer format, such as three bullet points and a recommendation
11

Ask for the change, precisely

A good request says what to change, what to keep, and how you will test it. Vague requests lead to surprise rewrites.

Request builder
12

Run it again and compare

Stop the app with Ctrl+C, start it again, and repeat your three test questions.

Terminal
npm start

Add one line to the change log at the bottom of AppPlan.md: what you changed and what you learned. A short log makes a strong final presentation.

13

Keep it or undo it

Before each change, save a copy of the working version. The simplest way is to copy the whole myapp folder and rename the copy myapp-v1, then myapp-v2, and so on. If you are comfortable with git, commit instead:

Terminal
git init
git add .
git commit -m "v1 works"

The starter's .gitignore already keeps local.env out of git, so your key will not be saved. If a change made things worse, ask the assistant to undo it, or go back to the saved copy.

14

Show it to others, without putting it online

For this course the app stays on your computer. Present it live from your laptop, or record a two-minute screen video of your three test questions and one improvement. Never send your local.env file or screenshots that show your key.

If you get stuck

Do not guess. Copy the exact error message, tell your assistant which command you ran, and ask it to explain the likely cause before it edits anything. Using this kit in your own class? I would like to hear how it went: get in touch.

Teaching resource 02

Multi-agent simulation: lead a team of AI agents

Business simulations in which participants run a committee of AI agents on a realistic decision. The agents advise, a person sets the limits and makes the final call, and a sealed set of outcomes shows what really happened.

  • MBA, executive and corporate teams
  • From one session to a multi-round course
  • No coding required
  • Fictional companies and data

Part of the AI Decision Desk, created with Prof. Ashish Desai.

How a simulation works

Each simulation drops participants into a fictional company that has to make one decision, and gives them a realistic file of records to make it with. Participants design the AI agents: what each agent is responsible for, what it looks at, what it must produce and what it must never do. They then run the committee, review its recommendation and decide.

The point is not to get the agents to sound clever. It is to practise supervising AI: writing precise instructions, keeping spending and risk inside limits that no agent can move, and checking the plan against reality.

DesignWhat makes it more than a prompt exercise

Each simulation is built around a real way AI systems go wrong, so blind trust gets caught.

Sealed outcomes

What actually happened stays locked until participants commit to a decision. There is no hindsight and no gaming.

Blind rounds

What the team learns is tested on a set of records the agents have never seen, so over-fitting shows up.

Hard limits

Budgets, caps and policy sit outside the agents. No instruction and no learning can move them.

Planted failure modes

Models that are wrong for one group, data that drifts, and messy records wait to be found by a careful team.

SamplesThree sample simulations

The full library has eight simulations across marketing, operations, strategy, sales, HR, content and trust and safety. These three show the range. Each one has a short introduction video.

Marketing · RetentionBeginner3–4 hours

The Festive Win-Back Desk

The situation. An online grocer wants to win back customers before a big festival. Its offer budget is fixed, and too many offers teach customers to wait for discounts. A model has already scored each customer's chance of leaving.

The decision. Who should receive an offer, and how generous should it be, when the budget cannot grow?

What participants practise. Writing precise instructions for each agent, keeping spending inside limits no agent can change, and comparing what was predicted with what actually happened.

Operations · LogisticsBeginner3–5 hours

The Dispatch Desk

The situation. A same-day delivery start-up has to assign a fresh batch of parcels to riders every morning. AI agents do most of the work.

The decision. Which parcels can the agents handle from start to finish, and which need a person to check them first?

What participants practise. Deciding the split between people and AI in a live process, describing each agent precisely, and weighing speed against the cost of a mistake.

The Hiring Panel

The situation. A retailer is hiring at scale for the festive season. AI agents score every candidate, and a human panel is accountable for the final shortlist.

The decision. Who makes the shortlist, and where should the panel step in and override the agents?

Common questions

Do participants need to code?

No. Participants write agent instructions in plain language and reason about limits and outcomes. Teams that want to build the agents in code can do so.

Which AI tools do the simulations work with?

They are tool-agnostic. Participants can run their committee in any capable AI assistant or agent framework. The learning is in the design, the limits and the checking, not in a particular product.

How long does a simulation take?

Beginner simulations run in a single session of a few hours. The advanced ones run over several rounds and can take up to about 20 hours of work.

Are the companies and data real?

No. All companies and records are fictional, built to behave like real business data, with problems planted for participants to find.
